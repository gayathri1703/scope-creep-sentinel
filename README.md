# Scope Creep Sentinel

An AI agent for freelancers, consultants, and small agencies that reads a
project's Statement of Work (SOW), watches incoming client requests, and
only interrupts the freelancer when there's a genuine scope decision to
make — instead of letting "small" requests quietly become unpaid work.

Built for the AWS Agents for Humans Hackathon 2026 — Professional Agents track.

## Why this is an agent, not a chatbot

- It reads structured context (SOW + project history) before every decision.
- One of its agents (the Decision Agent) has a **tool** it calls itself to
  look up the project's accumulated unbilled scope creep before judging
  risk — it decides what information it needs, rather than being handed
  everything up front.
- It maintains state across requests via the Scope Ledger (`data/history_*.json`).
- It only asks the human for input when the situation actually warrants it —
  in-scope, within-limits requests are logged silently.

## Architecture

Three Strands agents, each with one responsibility:
| Agent | Responsibility |
|---|---|
| `ScopeAgent` | Classify a request against the SOW, estimate effort |
| `DecisionAgent` | Judge whether to interrupt the freelancer + risk level (uses a ledger-lookup tool) |
| `CommunicationAgent` | Draft 3 client-facing messages dynamically |

Dollar amounts are always computed in Python (`hours × hourly_rate`), never
generated by the LLM — the model handles judgment and language, not arithmetic.

## Setup

You already have Python 3.12.5, a `.venv`, `strands-agents` 1.54.0, and AWS
CLI auth configured for `ap-south-1`. From the project root:

```powershell
.venv\Scripts\activate
pip install -r requirements.txt
```

No API keys are stored anywhere in this project — Bedrock calls use
whatever AWS CLI credentials are already active in your shell.

## Known limitations (MVP scope, on purpose)

- Client messages are simulated via keyboard input — no Gmail/Slack/Teams
  integration yet. Adding one later just means calling
  `project.handle_incoming_request(text)` with text pulled from that
  channel instead of `input()`.
- Revision-slot detection is a simple keyword heuristic
  (`"revision" in matched_sow_item`) — good enough for the demo SOW, but a
  dedicated `is_revision: bool` field on SOW items would be more robust.
- The Decision Agent's tool-calling-then-structured-output interaction
  hasn't been verified against a live Bedrock call yet (account was under
  AWS verification at build time) — see the note in `decision_agent.py`
  for the fallback pattern if the tool doesn't get invoked in practice.

## Future work (not needed for MVP, but the architecture supports it)

- Real client-channel integrations (email/Slack/Teams) feeding
  `handle_incoming_request()`.
- Amazon Bedrock AgentCore for persistent runtime/state if this moves
  beyond a local CLI demo — not forced into the MVP since it doesn't add
  value at this stage.
